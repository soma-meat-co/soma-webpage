2. Flujos

2.1 Acceso a las rutas de admin

  1. proxy(request) corre antes de cada página de /DMS/** (matcher: "/DMS/:path*").
  2. Sin sesión → redirige a /DMS/login (salvo login, reset-password y set-password).
  3. En /DMS/admin o /DMS/admin/**: session.getRole(); si no es admin/superadmin (isAdminRole) → redirige a /DMS.

Se llega a la lista desde el botón "Usuarios" de AdminPanel en /DMS. El proxy solo controla navegación: cada RPC y la Edge Function vuelven a validar is_admin() en Supabase.

2.2 Listar usuarios

  1. servidor UserManagementPage (async Server Component) llama en paralelo: 
    Promise.all([adminProvider.getAllUsers(), areasProvider.fetchAllAreas()])
    Las áreas se cargan aquí (no al abrir el diálogo) para el selector de "Editar".
  2. service getAllUsers() → supabase.rpc('get_all_users') y convierte cada fila (snake_case) a ManagedUser (camelCase).
  3. db get_all_users(): is_admin() o 42501; luego 
    profiles p JOIN auth.users u ON u.id = p.id LEFT JOIN areas a ON a.id = p.area_id
ORDER BY p.nombre, p.apellido_paterno, u.email
    Devuelve todos los usuarios (hay un TODO: de paginación en la RPC, el service y la página).
  4. render Si algo falla, handleError("UserManagementPage", err) y se muestra el mensaje en lugar de la lista. Si no, UserList users areas → un UserRow por usuario.
  5. render UserRow: nombre completo (o el correo si no tiene nombre), badge de rol, badge de área ("Sin área" si areaName es null), correo, y los botones EditUserButton y RemoveUserButton.

2.3 Invitar un usuario

Punto de entrada: "Agregar usuario" en la lista → /DMS/admin/invite-user.

  1. cliente InviteUserPage: formulario con nombre, apellido paterno, apellido materno (opcional) y correo. Al enviar llama la action con loading; muestra result.message en error o la confirmación con el correo.
  2. action inviteUserAction(input) inviteUser.actions.ts: no valida permisos; atrapa cualquier error y devuelve { ok: false, code, message }.
  3. service adminProvider.inviteNewUser(input) → supabase.functions.invoke('invite-user-as-admin', { body }) con el cliente de sesión (manda el JWT del admin). Si hay error, toAppError() lo traduce por el code del body.
  4. edge invite-user-as-admin:
    • withSupabase({ auth: "user" }) valida el JWT.
    • ctx.supabase.rpc("is_admin") con el cliente del usuario; si no es true → 403 forbidden.
    • parseBody: correo con @, nombre y apellido paterno no vacíos; normaliza (trim, correo en minúsculas).
    • El correo debe terminar en @somameat.com → si no, 422 email_not_institutional.
    • supabaseAdmin.auth.admin.inviteUserByEmail(email, { data: { nombre, apellidos }, redirectTo: INVITE_REDIRECT_URL }).
    • Registra profiles.created_by = id del admin (si falla, solo lo registra en logs).
    • Responde 201 { id, email }.
  5. db El INSERT en auth.users dispara on_auth_user_created → handle_new_user() crea el perfil con los nombres de raw_user_meta_data, role = 'user' y area_id = NULL.

El usuario nuevo queda sin área. El área se asigna después con "Editar" (flujo 2.5). El rol nunca se recibe del body: esta función no puede crear admins.

2.4 Activación de la cuenta

  • El correo de invitación lleva a INVITE_REDIRECT_URL (/DMS/set-password), donde el usuario crea su contraseña.
  • Al pasar auth.users.encrypted_password de vacío a no vacío, el trigger on_auth_user_activated pone profiles.activated_at = now().
  • activated_at = NULL significa invitación pendiente. get_all_users lo devuelve (ManagedUser.activatedAt), aunque la UI todavía no lo muestra.

2.5 Editar nombre y área

Punto de entrada: "Editar" en cada UserRow → EditUserButton.

  1. cliente handleOpenChange(true) carga en el estado los valores actuales del usuario (de la prop user, sin pedir nada al servidor). Campos en DmsDialog: Nombre, Apellido paterno, Apellido materno (opcional) y Área (select; "" = "Sin área").
  2. action editUserData(userId, { nombre, apellidoPaterno, apellidoMaterno, areaId }): hace trim(); nombre o apellido paterno vacíos → USER_NAME_REQUIRED sin llamar a la base; apellido materno vacío → null.
  3. service supabase.rpc('edit_user_data', { p_user_id, p_nombre, p_apellido_paterno, p_apellido_materno, p_area_id }).
  4. db edit_user_data: is_admin() o 42501 → UPDATE profiles SET nombres, area_id, updated_at = now(); 0 filas → P0002; área inexistente → 23503 (FK profiles_area_id_fkey).
  5. action revalidatePath('/DMS/admin/user-management') → la página se vuelve a pintar con el dato nuevo. El diálogo se cierra con { ok: true } o muestra message.

El rol no se edita en este flujo.

2.6 Eliminar un usuario

Punto de entrada: "Eliminar" en cada UserRow → RemoveUserButton.

  1. cliente Si useUser().user.email === user.email, el botón no se pinta (es la fila propia). Si no, abre un DmsDialog de confirmación.
  2. action removeUser(userId).
  3. service supabase.rpc('remove_user', { p_user_id }).
  4. db remove_user:
    • is_admin() o 42501.
    • p_user_id = auth.uid() → 22023 (nadie se elimina a sí mismo).
    • DELETE FROM auth.users WHERE id = p_user_id; 0 filas → P0002.
    • En cascada: profiles (ON DELETE CASCADE), y lo que Supabase Auth cuelga del usuario (sesiones, identidades).
    • Si el usuario aparece en documents.uploaded_by/deleted_by, areas.created_by o folders.created_by (FK sin ON DELETE) → 23503 y no se borra nada.
  5. action revalidatePath('/DMS/admin/user-management'); el usuario desaparece de la lista.

4. Base de datos

profiles

ColumnaTipoUso
idUUID PK → auth.users(id) ON DELETE CASCADEMismo id que la cuenta de Auth. Borrar la cuenta borra el perfil.
nombre, apellido_paterno, apellido_maternoTEXTSe llenan al invitar (metadata) y se editan con edit_user_data.

area_idUUID → areas(id) ON DELETE SET NULLUna sola área por usuario. NULL = sin área (estado de todo usuario recién invitado).
activated_atTIMESTAMPTZLo pone el trigger de activación. NULL = invitación pendiente.
created_byUUID → profiles(id) ON DELETE SET NULLAdmin que invitó. Lo escribe la Edge Function.
created_at, updated_atTIMESTAMPTZedit_user_data actualiza updated_at.

Permisos directos sobre profiles

  • SELECT: política "profiles: leer propio" → cada usuario solo lee su perfil.
  • UPDATE: "profiles: actualizar propio" + GRANT UPDATE solo en las columnas de nombre. Nadie puede cambiar su rol, área ni activated_at directamente.
  • Por eso la gestión de usuarios pasa por RPCs SECURITY DEFINER: con el cliente de sesión, un admin no podría leer ni editar perfiles ajenos.

6. Cómo extender

Paginación de la lista
Buscar los TODO: de paginación. (1) get_all_users recibe p_limit/p_offset (o un cursor) y devuelve el total. (2) getAllUsers recibe y pasa esos parámetros. (3) La página los lee de searchParams y pinta controles de página.
Búsqueda y filtro por área
UserSearch es solo visual. Opciones: filtrar en el servidor con parámetros en get_all_users (necesario con paginación), o filtrar en el cliente la lista ya cargada.
Editar el rol
Agregar p_role a edit_user_data (o una RPC aparte). Debe cumplir la regla de privilegios: nadie asigna un rol mayor al propio. Después: campo en EditUserInput, en el rpc() y un select en EditUserButton.
Mostrar invitaciones pendientes
ManagedUser.activatedAt ya llega; basta un badge en UserRow cuando es null.
Permitir eliminar usuarios con documentos o carpetas
Migración que cambie las FK de documents.uploaded_by/deleted_by, areas.created_by y folders.created_by a ON DELETE SET NULL. Sin eso, remove_user responde 23503.
Otra operación de admin
Si solo necesita SQL: RPC con is_admin() primero → método en AdminProvider + SupabaseAdminService → código en AdminErrorCode → action con handleError y revalidatePath. Si necesita la secret key (API de Auth admin): Edge Function, según ADR-007.

7. Comportamientos no obvios y límites actuales

ComportamientoConsecuencia
get_all_users trae a todos los usuarios.Con muchos usuarios la página será lenta. Pendiente: paginación (TODO:).
Los usuarios invitados quedan con area_id = NULL.Aparecen como "Sin área" hasta que un admin los edita.
Las RPCs solo validan is_admin().Cualquier admin puede editar o eliminar a otro admin o a un superadmin. Solo se impide eliminarse a sí mismo.
remove_user borra de auth.users con SQL.No pasa por la API de Auth ni por una Edge Function. Es irreversible: no hay soft delete de usuarios.
Usuarios que subieron documentos o crearon carpetas/áreas no se pueden eliminar.23503 → "No se puede eliminar: el usuario tiene documentos, carpetas o áreas a su nombre."

revalidatePath refresca solo la página de quien hizo el cambio.Otros admins ven el cambio al recargar o al vencer su Router Cache.
El área del usuario hoy es informativa.La lectura de documentos no se filtra por área (can_access_documents() solo pide sesión).
UserSearch no tiene funcionalidad.Búsqueda y filtro son placeholders visuales.

8. Glosario

Perfil (profiles)
Datos del DMS de un usuario (nombre, rol, área). Una fila por cuenta de auth.users, con el mismo id.
Invitación
Cuenta creada por un admin sin contraseña. El usuario la activa al crear su contraseña desde el correo.
SECURITY DEFINER
Función SQL que corre con los permisos de su dueño, no de quien la llama. Se salta RLS, así que debe validar permisos por sí misma.
Edge Function
Función que corre en la infraestructura de Supabase (Deno). Aquí se usa para operaciones que necesitan la secret key.
Secret key (service role)
Credencial de Supabase que se salta RLS. Solo existe en Supabase (Edge Functions), nunca en Next.
Proxy
src/proxy.ts (antes llamado middleware). Corre antes de cada página del DMS y decide si deja pasar o redirige.
